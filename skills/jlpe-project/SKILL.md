# JLPE project orientation

Use when working on the JLPE repo (`C:\\Fragments\jlpe`, `github.com/Seeeaaa/jlpe`): a Dockerized JupyterLab environment published as `vyxan/jlpe_image`. python:<X.Y>-slim-trixie base (read the pin from the Dockerfile; it moves via the python-minor ladder), `uv` as package manager, CI-only. This skill is a MAP, not a second copy of the rules; the authoritative rules live in `AGENTS.md` in the repo (untracked by design - see Security posture). Deep history lives in the references, loaded on demand: `references/audit-ledger.md` (full audit findings and triages) and `references/image-anatomy.md` (layer, GPU, and dependency-tree findings).

## Repo map

- `pyproject.toml` - top-level pinned deps only, grouped under `[dependency-groups]`: `ml`, `data`, `visualization`, `jupyterlab`, `theme`. Every dep pinned to `==version`, no ranges. `package = false`, `environments = ["sys_platform == 'linux'"]` (image is Linux-only).
- `uv.lock` - exact resolved versions. NEVER edit locally; CI regenerates it. This is the single most important rule and trips agents constantly.
- `Dockerfile` - multi-stage (uv + python:<X.Y>-slim-trixie); base images pinned by digest; `APT_BUST`/`VERSION`/`REVISION`/`CREATED` args stamped by build.
- `.gitignore` - intentionally EMPTY; acts as a tripwire (any unplanned file must surface in git status). Do not add entries.
- `.gitattributes` - forces LF repo-wide. Do not regress any file to CRLF.
- `.github/workflows/` - the CI/CD (see below); `.github/actions/` - composite actions (read-python-version, read-uv-version, summarize-deps).
- `.github/dep-probes/candidates.json` + `tests/check_<name>.py` - probe queue (folded into `tests/smoke/` when a lib is enabled).
- `tests/smoke/test_<name>.py` - permanent smoke tests, run by build.yml.

## Adding a library

Two paths, both end in the same mechanism:

1. **Direct add (normal case):** add `name==version` to the right `[dependency-groups]` group in `pyproject.toml` and drop a `tests/smoke/test_<name>.py` file. The smoke-test job loops over `tests/smoke/*.py`, so no `build.yml` edit is needed. Do NOT touch `uv.lock`.
2. **Compatibility probe (previously-excluded / may-not-resolve libs):** add a `candidates.json` entry + a `.github/dep-probes/tests/check_<name>.py` probe. Nightly `check-upstream.yml` runs `dependency-probes` -> `probe`: `uv add` to resolve, pin the exact version, run the probe. Only when resolution reached upstream latest (update-availability gate) does it remove from `candidates.json`, `git mv` the probe into `tests/smoke/test_<name>.py`, and open an `enable-dep-<name>` PR; below latest the candidate stays queued and re-verifies nightly. A resolver back-off below latest is legal (requirements conflict with an existing pin) - the probe enforces update availability on the PR-creation path, never on run status (red nightly runs for a known ceiling re-create red-X desensitization).

## Smoke-test contract (hard, non-negotiable)

A smoke test / probe must be **network-free and deterministic**. It runs against the pinned stack in CI and only asserts API-surface integrity (imports, round-trips, shape/finiteness on synthetic data) - with seeded data generation. Never validate forecast accuracy, never make live requests (`fetch_*`, `load_markets`, etc.). See `tests/smoke/test_ccxt.py` and `test_narwhals.py` for the canonical shape.

## Caching decisions (audited 2026-10-04, zero-change; depth in references/audit-ledger.md)

Build caching is complete and measured-optimal: buildx gha cache mode=max (buildkit-blobs ~2 GB), trivy DB cache (default cache: true), setup-uv metadata cache. Do NOT re-propose a setup-uv wheel cache for probe/intermediate jobs: uv sync takes 7-22s on a fresh GH runner, and a 2.4 GB per-lock-hash entry would churn the 10 GB LRU and risk evicting the buildkit blobs. Dockerfile instructions after COPY VERSION (ARG/LABEL/EXPOSE/ENTRYPOINT) are config-only, create no layers, and reordering them has zero measurable effect.

## CI/CD map

- `build.yml` - core pipeline, main + PR. `changes` (path filter on Dockerfile/pyproject/uv.lock/VERSION) -> `stamp-date` (bumps version date, pushes `[skip build]` commit straight to main) -> `build` (buildx + log-only trivy scan + apt security publish gate) -> `smoke-test` (one loop step that pipes every `tests/smoke/*.py` into a container) -> `push` (Docker Hub: sha, full version, python version, latest).
- `check-upstream.yml` - consolidated daily (20:00 UTC) + on-main-push + manual: `versions`, `bump-base` (python/uv via crane, inputs format-validated), `intermediate-deps` (uv lock --upgrade), `dependency-probes`/`probe`, `python-minor` (ascending minor-version ladder; crossing procedure, PR-review checklist, and feasibility probe in references/python-crossing.md, probe script scripts/py-minor-feasibility.py). Manual runs take a `checks` csv (empty = all) and a `probe_only` single name.
- `update-lock.yml` - regenerates `uv.lock` after every non-main push (required check). Skips dependabot pushes (they get a read-only token and no secrets; without the skip its checkout dies with 'could not read Username').
- `update-pr-branches.yml` - merges main into open PR branches with `[dependabot skip]`; fires on main push, on PRs touching itself (live self-test), and on check-upstream completion (`workflow_run` - the trigger that opens the CPR safe-merge window; CPR branches get the merge only while their owner workflow is idle).
- `reconcile-code-scanning-alerts.yml` - daily 21:10 UTC + on-main-push + manual: scans the published image with trivy (SARIF), refuses to upload an empty scan (DB outage would close all alerts as fixed), uploads to the Security tab via codeql-action/upload-sarif with fixed ref+category AND sha as a pair (PR #257 + the ref-alone sha fix #258: upload-sarif requires ref and sha together when either is provided; with no checkout step the action cannot derive the sha itself and the upload dies - seen in practice as "Both 'ref' and 'sha' are required if one of them is provided"); PR-triggered runs never touch the tab.
- `dependabot.yml` - daily `uv` + `github-actions` updates.

## Workflow rules (from AGENTS.md - read the file for full text)

- Branch per change, never commit to main; every change lands via a PR the owner reviews. One commit per change. Chain `git fetch origin main` into every `git checkout -b ... origin/main` (main moves constantly here: daily stamps + merges make stale remote-tracking refs).
- Semantic commit messages: feat/fix/docs/style/refactor/perf/test/build/ci/chore.
- `uv.lock` is CI-owned; never generate/edit it locally, no local `.venv`. Dependency resolution (uv add / lock / compile) runs ONLY in cloud CI, never locally.
- Version format `{python}+{variant}.{date}`; the daily stamp-date job owns the date and its `[skip build]` marker - never remove the marker.
- ASCII-only everywhere (no en/em dashes, no Unicode arrows - use `->`).
- Third-party GitHub Actions pinned to full commit SHAs; `actions/*` and `docker/*` can use version tags.
- PR/issue/comment bodies: each prose paragraph is ONE long markdown line; never hand-wrap (single newlines render as hard breaks). Markdown structure is ASCII-safe; separate blocks with blank lines.

## Security posture (verified 2026-10-01, SARIF severity filter resolved 2026-10-04; full ledger in references/audit-ledger.md)

- All external action refs SHA-pinned (trivy-action at the post-incident safe line v0.36.0+); every top-level dep exact-pinned; all uv.lock URLs on pypi.org/files.pythonhosted.org; secrets scan of tree and history clean; job permissions least-privilege (verified by #244/#245); timeout-minutes on every job (#243); bump-base registry inputs format-validated before sed (#247).
- AGENTS.md is NOT tracked in the repository (hidden via .git/info/exclude). OWNER RULING: untracked is the design decision, not a gap - do not flag it in audits and do not open PRs to track it.
- Container runs as root by design; a naive USER switch is WORSE than staying root (apt gate dies vacuously, venv stays unwritable, GPU unproven as non-root - tradeoffs in references/audit-ledger.md). JupyterLab smoke `--allow-root --token='' --ip=0.0.0.0` is accepted for hermetic CI (container never exposed).
- Trivy image-scan alerts are keyed by (ref, category) of the upload analysis, not by digest: same-ref uploads update alerts in place and never accumulate (verified: 53 alerts created on exactly two dates across dozens of builds). The never-closing ledger in #193 came from a per-digest ref, not from SARIF itself. An alert with an empty 'Fixed Version:' is the unfixed/deferred category (no trixie-security release yet); it is correctly open while the finding is present in the current scan. The Security tab undercounts by design when no upload runs (2026-10-03: 55 live findings, 53 alerts - 2 new libexpat CVEs existed in no alert); PR #257 restores the daily SARIF upload with ref=refs/heads/main + category=.github/workflows/build.yml:build (the pre-#193 analysis key, so the first upload replaces the same analysis and the old alerts roll over natively) and deletes the manual dismissal loop (a dismissal loop under native dedupe dismisses alerts the next upload re-opens). upload-sarif needs sha passed alongside ref when either is given (fix #258: github.sha; the action cannot derive it without a checkout step). Cutover verified 2026-10-04: analyses on refs/heads/main carry category .github/workflows/build.yml:build; 249 open alerts = 249 live findings (225 pre-cutover alerts rolled over natively, 24 new, zero duplicates). Trivy SARIF trap: in format=sarif the pinned trivy-action v0.36.0 entrypoint unsets TRIVY_SEVERITY unless limit-severities-for-sarif: true is passed, so reconcile-code-scanning-alerts.yml's severity: CRITICAL,HIGH was silently ignored and all 249 findings (102 LOW, 87 MEDIUM, 5 UNKNOWN) reached the Security tab. Resolved by #262 (2026-10-04): the flag is set, the first filtered upload closed the ~194 low/medium/unknown alerts as fixed, and 55 open alerts remain, all HIGH (verified live via gh api 2026-10-04); low/medium findings are now tracked on no CI surface - the full picture needs a manual trivy run.
- Reconcile triggers fire before the build published by that same push finishes (~12 min): reconcile scans the previous published image (safe direction; only delayed dismissals, never hidden). Reconcile's SARIF scan needs limit-severities-for-sarif: 'true' or trivy-action silently unsets the severity filter (fixed in #262; the first filtered upload landed 2026-10-04 and closed the low/medium/unknown wave). The empty-scan guard now trips if the image ever becomes genuinely HIGH/CRITICAL-clean: 0 filtered results is indistinguishable from a DB outage, the guard fails loudly (acceptable, needs a rethink when the image is clean).
- sha_pinning_required is ON at repo level (2026-10-04): every external uses: must be a full 40-hex SHA or the workflow fails to start; bare-major `# v4` comments on SHA pins stall Dependabot's github-actions bumps - always comment the exact version.
- Dependabot github-actions stalls: check pinned SHAs against latest tag commits directly (resolve annotated tags through object.url); do not wait out a stall that already exceeds ~2 weeks with live releases.

## Dependabot-alert triage method

Before dismissing or fixing: read the alert object via `gh api repos/Seeeaaa/jlpe/dependabot/alerts` (anonymous curl needs auth for alerts endpoints), check the CURRENT uv.lock pin against the advisory's vulnerable range. Root-causing a locked transitive: scan requirers' PyPI requires-dist metadata - awk over uv.lock `[[package]]` blocks for requirers, strip TOML quotes from the pinned version, then `curl pypi.org/pypi/<pkg>/<ver>/json` per requirer. NOT local resolution: the linux-only environments make `uv pip compile` return an empty set on the Windows host (structurally impossible, not a bug). A requirer's exact pin (e.g. ccxt -> urllib3) caps the transitive through the nightly `uv lock --upgrade`; the fix is the requirer's own bump.

## Verification procedure for the published image

OWNER RULING (2026-10-01): image verification does NOT use local Docker - everything is configured to run in GH cloud. ## Verification-script job-map trap (Oct 3 2026)

A structural verify pass over BOTH workflow files must use each file's real job list: check-upstream.yml has no 'build' job (it has bump-base/probe), so a shared assertion keyed on jobs['build'] crashes with a bare AssertionError naming the wrong file - a diagnostic red herring that looks like the edited file is broken. Print the file's job list first (or iterate per-file assertions with distinct messages); a per-file second run confirmed the edit was correct all along.

## Manual-dispatch trap (created a duplicate PR in practice, Oct 1 2026)

A manual dispatch of a multi-job check workflow selects ALL jobs (empty checks input = all) - including the PR-creating ones. Dispatching check-upstream to live-test one job ran intermediate-deps, whose create-pull-request force-pushed the fresh lock onto the EXISTING PR branch (5 force-pushes on the open PR's timeline) instead of creating a new branch, and GitHub opened the resulting PR with base = the dispatch ref (a feature branch), not main. Resolution: closed the duplicate WITHOUT branch deletion (deleting would kill the canonical PR's head; create-pull-request's delete-branch fires only on merge). Lessons: (1) to live-test one job, pass the `checks` input (e.g. `checks=python,uv` for bump-base only); (2) create-pull-request updates an existing branch by force-pushing onto it - any run whose `branch:` name collides with an open PR's head can rewrite that PR's head; (3) a PR created from a workflow_dispatch gets base = the dispatch ref.

## Pitfalls learned from real fixes

- Version-extraction grep logic lives in composite actions. Stamp-date's in-loop grep is NOT a duplicate: it deliberately re-reads the Dockerfile on every push-retry attempt (a concurrent base-bump PR merging main mid-run changes the pinned digest). Do not dedupe it into a composite.
- The fold step used `cp`, leaving a stale probe duplicate after a lib was enabled; changed to `git mv` + `.github/dep-probes/tests` in the PR add-paths; the smoke-test loop auto-discovers tests/smoke/*.py (no build.yml step-insertion).
- mlforecast `lag_transforms` values must be mlforecast's own transform objects wrapped in a list, not raw numpy functions: the functions run inside a numba `@njit` block, and `np.mean` is a NumPy 2 `_ArrayFunctionDispatcher` that numba cannot type.
- The `patch` tool's fuzzy matcher can silently mangle YAML indentation and match the WRONG anchor (an exact-match job anchor like `  push:` also matches the `on:` trigger block). For workflow edits: programmatic str.replace against exact multi-line anchors (include the `needs:` line to disambiguate), verify by counting lines/markers, and `yaml.safe_load` via `uv run --no-project --with pyyaml` before pushing. Pushing a workflow PR with a silently-skipped insertion costs a whole round-trip.
- execute_code can return success with swallowed exceptions and zero captured output on this host: verify file edits with an independent read (terminal grep/awk) or add explicit try/except + START/END markers before trusting the result.
- execute_code cannot shell out to bash on this host: its subprocess goes through WSL (execvpe(/bin/bash) fails, WSL is not installed). The terminal tool uses git-bash instead - run dry-runs of CI shell pipelines (grep/sed/awk chains) through terminal, never subprocess in execute_code.
- Native Windows binaries invoked from the git-bash terminal do not get MSYS paths translated: a `/tmp/...` path argument reaches them untranslated and fails with FileNotFoundError. Convert with `cygpath -m` (yields C:/-style) for any file a native tool must read (python, gh --body-file, etc.).
- README minor-version rewrites must be boundary-guarded: a bare `s|Python 3\.13|...|` match mangles the historical versioning example ("Python 3.13.14" -> "Python 3.14.14"). Guard with `([^.0-9]|$)` after the minor and `/lgbm_gpu/!` negation for the outdated-tag row; the python-minor gate in check-upstream.yml carries the corrected pattern.
- python-minor crossing gate (PR #261, Oct 2026): job in check-upstream.yml, csv component `python-minor` (default csv + nightly + targeted dispatch; the bump-base component builder deliberately does NOT list it, so checks=python-minor runs only versions -> python-minor). LADDER semantics: all docker-library minors above the pin, ascending, newest patch tag per minor; PR opens for the FIRST candidate passing both gates (uv lock + uv sync --no-build + test_all_top_level_imports.py), never a skip over a ready intermediate minor and never a deadlock on an unready newest (a fresh .0 minor ships no wheels for the heavy stack and simply queues green until they appear). PR branch migrate-python-<minor>, force-updated nightly while open. Verified in production on first merge: the job fired on its own merge push and opened the crossing PR within a minute - expect an auto-PR whenever a workflow change adds a PR-creating job, and close any stale one before a follow-up experiment that moves the pin. Also verified on a real two-rung ladder (pin 3.12, candidates 3.13.16 and 3.14.8): the walk chose the NEAREST viable rung and never skipped to the newest - the defining ladder semantic, now proven live, not just in fixtures. Dispatching it on a feature branch would open the migrate PR with base = that branch (the workflow_dispatch-base trap) - only dispatch after the gate PR merges to main. Review criterion for a crossing PR's uv.lock: pure platform transcription - zero version deltas, cp3OLD wheel URLs re-tagged cp3NEW, abi3/pure counts unchanged, the marker-conditional package(s) the only drop; any version delta means the re-resolve drifted a pin and the PR needs a second look (full checklist: references/python-crossing.md). Crossing procedure, feasibility probe, and manual pin-change recipe: references/python-crossing.md + scripts/py-minor-feasibility.py.
- awk pitfall (found by dry-run, would have shipped broken): split() in the pattern position of an awk rule is a SYNTAX ERROR, not a valid pattern - the multi-line program then degrades silently (filter ignored, duplicated output). split() must live in a BEGIN block. Also compare minors numerically ($1*100+$2), never as strings: awk string compare ranks "3.9" > "3.10" lexically.
- Dry-run harness discipline on Windows: Python-written .sh fixtures MUST use write_text(..., newline="\n") or CRLF sneaks in and bash/awk misparse (duplicated rules, phantom matches). Keep ONE source of truth per tested pipeline: the fixture generator carries its own copy of the awk program - when the workflow's pipeline is patched, patch the generator too, or the dry-run validates a stale program.
- CPR-branch race (fixed in PR #274, Oct 2026): update-pr-branches.yml and the check-upstream PR-creating jobs (intermediate-deps, bump-base, probes) both fire on every push to main; merging main into a CPR-owned branch while create-pull-request holds a fetched ref kills its force-with-lease push ('cannot lock ref ... is at X but expected Y', red X on a main push event, stale lock until next nightly). Fix: CPR_BRANCH_RE in update-pr-branches.yml matches exactly the branch families create-pull-request owns (upgrade-intermediate-deps, bump-python-version, bump-uv-version, enable-dep-*, migrate-python-*), and a matched branch is skipped ONLY while the owner workflow check-upstream.yml has a queued or in_progress run - the only window where the collision is possible; when the owner is idle the script merges main into the CPR branch instead (mechanism in the lifecycle bullet below); dependabot branches always keep the merge (it is load-bearing for them, and the [dependabot skip] marker preserves Dependabot branch management). Any NEW create-pull-request branch name added to check-upstream.yml must be added to CPR_BRANCH_RE too, or the race returns. The workflow's pull_request paths-trigger on its own file doubles as a live test harness: a PR touching it logs skip/update lines against the real open-PR list without merging anything.
- CPR-branch behind-state lifecycle (the cost of the #274 skip): a create-pull-request branch's updater is its owning job re-running - the nightly cron, or a main merge whose files hit check-upstream's push paths (Dockerfile/pyproject.toml/uv.lock/check-upstream.yml) - plus the owner-idle safe-merge at the end of this bullet. Even a paths-matching merge leaves the branches stale: the CPR owners rebuild from pre-merge main, then stamp-date lands a VERSION-only commit in main about a minute later, and the stamp push deliberately does not re-trigger check-upstream (VERSION is not in its push paths - adding it would loop the pipeline), so after EVERY content merge all open CPR PRs sit exactly 1-behind on the stamp commit until the owning run completes (the workflow_run trigger then heals it; before that trigger the wait ran to the next nightly). Workflow-file merges that are not in the paths never wake the owners at all. The "out-of-date" banner is strict protection demanding checks re-run on a head containing current main; green checks on a stale head never clear it. Manual heal that wakes every owner at once: `gh workflow run check-upstream.yml --ref main -f checks=python,uv,intermediate,python-minor` (subset inputs wake only what you name). Auto-merge (`allow_auto_merge`, enabled at repo level) removes the manual Merge press but never heals behind. Owner preference: zero manual Update-branch presses - branch freshness must stay automated. Satisfied by the owner-idle safe-merge in update-pr-branches.yml: before the CPR skip, query in-flight runs of check-upstream.yml (github.rest.actions.listWorkflowRuns, statuses queued + in_progress); owner idle -> repos.merge main into the CPR branch with the same [dependabot skip] message - zero content risk, because the owner's next run resets the branch to current main and discards the merge commit; owner running -> keep the skip. Push-triggered runs of update-pr-branches CANNOT heal the window: a content push starts this workflow and the owner concurrently (same event), and the stamp push fires it while the owner is still in-flight, so every push-path run observes the owner running and correctly skips - the safe-merge window opens only at the owner's COMPLETION, a moment no push event marks. The trigger that catches the open window is update-pr-branches.yml's `on.workflow_run` (types: [completed], workflows: [the owner's Actions-tab NAME, e.g. "Check upstream drift", not the filename]): it fires exactly when the running-owner query can first return idle, and the script's own check re-validates (any other in-flight owner run still skips). General orchestration rule: when a conditional action's guard flips at 'another workflow finished', subscribe to THAT event - push-triggered runs of your workflow overlap the other workflow's entire lifetime and never observe the flipped state (general form in the github-actions-authoring skill). The runs query needs `actions: read` on the JOB-level permissions block: a job-level `permissions:` replaces the workflow-level one entirely, so a workflow-level-only grant is silently dropped for the job; without the grant the query throws and the whole github-script step fails (closed: no merges happen, healing stops, step goes red).
- github-script workflow edits: verify the exact script payload in node before pushing - wrap the script text in new Function with a stubbed `github` object (paginate + rest.merge recording every call) fed the live open-PR list from gh, run one case per logic state (every branch of any conditional, plus the pull_request test-run path), and assert the merge-call set per case. The workflow's pull_request paths-trigger on its own file then replays the same logic against live data inside the PR's own checks (logs only, merges nothing) - use it as the live second layer. A permission needed by an in-script API query surfaces here as a thrown call: reason out fail-open vs fail-closed BEFORE writing the safety comment, and write the comment to match the real semantics (an unhandled rejection fails the whole github-script step, it does not degrade a flag to falsy).
- Dependabot schedule stall (diagnosed 2026-10-13): the uv updater classifies an unsatisfiable PROPOSAL (latest version above a requirer's cap, e.g. pyarrow 26 vs mlflow 3.17.x's pyarrow<26) as job-fatal dependency_file_not_resolvable (upstream bug: fix PR dependabot-core#13892 still open; issue #13886 closed without the fix landing) - and ONE exit-1 update job makes GitHub drop ALL the repo's update jobs from the daily schedule, both ecosystems, alerts unaffected (they are dependency-graph driven). Diagnose from the dynamic "Dependabot Updates" workflow (id 317304242): newest run time + per-job logs via gh run view <id> --log. Its PR history filter is author login "app/dependabot" (NOT "dependabot[bot]"). Wake-up: any edit to .github/dependabot.yml re-registers both jobs and fires one out-of-band full pass - satisfiable bumps still get PRs before the fatal abort (shap precedent: PR #284 created seconds before the pyarrow abort in the same dying run). While the upstream bug is live, one wake = one pass and the schedule dies again the same night. OWNER RULING: NO ignore rules ever - every dependency keeps its daily evaluation; a failed attempt (pyarrow unsatisfiable against mlflow's cap) is a legitimate daily outcome reported in logs, never filtered. Groups do not help: grouping changes PR batching, not the update_files resolution path, the same fatal classification fires.
- Stall watchdog (wake-dependabot.yml, landed via PR #298): makes the wake fully automatic per owner ruling. Hourly probe; newest "Dependabot Updates" run older than 26h -> replace the single "# Wake-up Touch" datestamp comment line in dependabot.yml (insert before updates: when absent) -> create-pull-request opens the wake PR on branch wake-dependabot (PAT_FOR_BOTS) -> gh pr merge --auto --squash arms auto-merge; required checks (build, smoke-test, update-lock, ~8 min) gate the landing; the config change then re-registers both jobs. Guard step: if a wake PR is already open, re-assert auto-merge and touch nothing. Branch protection has no required reviews (checks only), so auto-merge works. Self-retiring: a healthy nightly schedule never trips the 26h threshold, so the day the upstream fix (dependabot-core#13892) ships or the blocking cap lifts, the watchdog goes silent. update-pr-branches.yml: CPR_BRANCH_RE gained wake-dependabot, and the owner-idle gate queries BOTH owners (check-upstream.yml + wake-dependabot.yml) - an in-flight run of either skips all CPR-branch healing (deliberately conservative; retries on next trigger).
- Dependabot schedule resurrection paths (observed 2026-10-14): any pyproject.toml pin merge on main re-triggers the uv update job AND re-registers the whole schedule (the four pin merges of Oct 14 produced uv runs at 15:17/15:59 and the genuine nightly 22:53 fired on its own); uv.lock-only merges (CPR intermediate-deps) do NOT resurrect. So the stall only persists through quiet windows with no pin merges - exactly the gap the watchdog covers. Two more wake paths exist besides the config touch: the Dependabot tab's manual "Check for updates" button (both ecosystems at once, no commit trace - the probable trigger of the Oct 14 08:14 pass, which predated the watchdog's first probe) and the manifest-change re-trigger (uv ecosystem only).
- GitHub drops scheduled workflow runs under load; top-of-hour minutes are the documented worst window. The wake probe at :05 fired only 5 of ~30 hourly ticks in its first 31h (gaps to 5h22m); the 26h threshold absorbed the granularity, and PR #305 moved it to :41. General rule: never place a short frequent cron at :00-:10; size wake thresholds to tolerate sparse probe cadence.
- Pre-push verification set for workflow edits (all used for #298): node harness over the exact extracted github-script payload (new Function + stubbed github, assert the merge-call set per logic state), yaml.safe_load via uv run --no-project --with pyyaml, sed dry-run on fixture variants (target line present vs absent, LF-written fixtures), live read-only dry-run of probe bash with real gh api, plus the update-pr-branches pull_request self-test as the live second layer.
- update-pr-branches vs Dependabot-head PRs after lock churn: merging main into a dependabot/* branch whose uv.lock predates sibling dep merges dies with "Skipped PR #N: Merge conflict" - the skip is correct behavior (the script never resolves conflicts), the rebase belongs to Dependabot (its own cycle or a @dependabot rebase comment), and the PR keeps its checks. Expect it whenever several dep PRs merge close together; not a workflow fault.
- Same-tag digest-refresh PRs (bump-base title "refresh pinned digest for python:<tag>") are normal: docker-library rebuilds a published tag in place, so the digest changes while the version does not - read the title (refresh vs bump) before reconstructing history. Same CPR families for skip/behind purposes.
- Worktree procedure for PR-branch edits while the main checkout is dirty on another branch: git worktree add <path> <branch>, edit/commit there, push with the credential bypass, git worktree remove --force. The main checkout's uncommitted changes are untouched. If push is rejected with 'fetch first', it is update-pr-branches.yml having merged main into the open PR branch (bot commit 'chore: merge main into PR branch [dependabot skip]') - rebase onto origin/<branch> and push again; the rebase is clean because the merge only touched other files. Since PR #274 this only happens for dependabot-head PRs; CPR-owned branches are skipped.
- Resolving a conflict on a PR branch: build the merge from origin/<branch>, never the local ref. git worktree add checks out the LOCAL branch, which can lag origin by commits that exist only remotely (the update-lock regenerate commit, bot merge-main commits); a merge built on the stale ref silently drops the CI-generated lock from the PR and pushes without any error. Fetch origin <branch>, git reset --hard origin/<branch> in the worktree, merge, resolve, then verify the merged tree (uv.lock requires-python window, Dockerfile FROM pair) before pushing.
- A smoke-only failure on a crossing PR is the python-minor gate's designed blind spot, not necessarily a bad crossing: the gate proves resolve/install/top-level imports, only the in-container smoke loop exercises runtime behavior inside library calls. CPython 3.14 flips the Linux multiprocessing default to forkserver; a stdin-piped smoke whose library builds a multiprocessing.Pool dies re-importing '<stdin>' (tsfresh extract_features is the known case). Fix the smoke to its serial path (tsfresh: n_jobs=1 selects the serial MapDistributor) - spawn fails the same way under stdin. Depth: references/python-crossing.md.
- build.yml's cancelled 'push' job on pull_request runs is the concurrency group canceling superseded duplicate runs - same-minute duplicates come from update-pr-branches merge-main or from update-lock's regenerate commit; the push job never publishes on PR events by its if-guard, so a cancelled empty push job is benign noise, not a failure. The cancelled duplicate's QUEUED jobs can also surface as 'fail' in the PR statusCheckRollup until the live run finishes - read per-run job conclusions (gh run view <id> --json jobs), never diagnose a PR from gh pr checks alone.
- gh pr list has no --paginate flag (that is gh api); use --limit N for the JSON list.
- authenticate: gh CLI is logged in as the repo owner; anonymous api.github.com calls fail on alerts endpoints with 'Requires authentication'.
